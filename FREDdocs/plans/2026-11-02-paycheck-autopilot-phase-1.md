# Paycheck Autopilot Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The 23 task sections live in sibling files under `FREDdocs/plans/2026-11-02-paycheck-autopilot-phase-1/` (one file per task, each under 75,000 characters so a single Read call loads it); this file is the header, constraints, rulings, prerequisites, task index and seams. Task 23 was added after the first 22 and keeps its number, but it runs right after Task 02 (see the Task index).

**Goal:** Run Paycheck Autopilot in shadow mode on Plaid Sandbox during the beta (spec section 14, decision 13: `enabled=true, shadow=true, pulls.enabled=false`): sync, the recurring reader, detection, streams, events, shadow-skipped cycles, the inbox drainer, the 22:30 reconcile, Item-state handling, the update-mode consent path and reconnect card, the admin surface, the shadow report and `NotificationGate`, gated on the ops alert channel and the heartbeat digest. Nothing moves money that does not move today. Exit: two pay cycles tuned, zero user-facing DETECTED notices, `plaid.items.billable` reconciled against the first invoice.

**Architecture:** Pipeline first. Pure detection rules (`paycheck.detect`, T09) come before any I/O, and one orchestrator, `PaycheckSyncPipeline` (T14), stands in front of every entry point (webhook drainer, reconcile, status endpoint, admin and dev verbs); nothing else calls `/transactions/sync` or `/transactions/recurring/get`. Plaid is reached only through `PlaidGateway` (T06), which classifies every error into a `PlaidErrorClass`. Sync writes `paycheck_events` (T07, T08); `evaluate` scores streams and mirrors the result onto the MANUAL schedule row when one exists (T11, R1); cycles are written `SKIPPED SHADOW_CONFIRMED` through `CycleGateChain` (`ShadowGate`, `KillSwitchGate`, T12, R7); `PlaidItemStateService` (T13) owns webhook- and error-driven Item state and the three non-blocking Item-state holds; the 22:30 reconcile (T15) handles misses, dormancy, retention, REJECTED Items and the fallback sync. Ops alerts land in a dedupe ledger and go to a logging or webhook provider (T04), and a 09:07 ET heartbeat sends every gauge (T05). Operators use a shared-secret admin surface written to `admin_actions` (T17, T18) and read the shadow report (T19). The only DDL is `V11__ops_alerts_and_admin_actions.sql`: two `CREATE TABLE IF NOT EXISTS` (T01); V6 already holds every paycheck table, and T02 maps them. The only user-visible changes are the reconnect card, the RECONNECT notice and the update-mode consent path (T16, T21). **First sync, stated plainly:** in Phase 1 a user's first `/transactions/sync` is started by the 22:30 reconcile (any consented-or-unknown OK Item with no cursor) or by an operator. The backend half of the screen 1 trigger already ships in T16 (`GET /api/paycheck-detection/status` enqueues the first sync the first time it is polled for an Item with no cursor), but the app does not call it in Phase 1. Phase 2 builds screen 1, whose poll of that endpoint becomes the trigger, and at that point the reconcile stops initializing users who have not reached screen 1 (decision 7: nobody is billed for a subscription before they reach the schedule page).

**Tech Stack:** Spring Boot 3.5.0, Java 17, Gradle, MySQL 8 with Flyway (`ddl-auto=validate` in every profile), plaid-java 46.0.0, jjwt 0.11.5, Caffeine 3.1.8, JUnit 5 + Mockito + AssertJ, Angular 19 + Ionic 8 (Karma specs), Capacitor 8 iOS.

**Spec:** `FREDdocs/specs/2026-10-19-paycheck-autopilot-design.md` (approved 2026-10-19; section 14 defines Phase 1, section 15 holds the 23 decisions). Locked UI: `FREDdocs/specs/paycheck-autopilot-mockup.html`. Origin: `FREDdocs/specs/paycheck-autopilot-spike.md`.

**Handoff:** `FREDdocs/handoff-paycheck-autopilot.md` (the code as it is after the analytics merge; it overrides the spec wherever the two disagree). Controller rulings and their reasons: `.superpowers/phase1-planning/inputs.md` (restated below). Decomposition contract: `.superpowers/phase1-planning/design-final.md`. Repository state targeted: `develop` at 137998c (2026-11-02), worked on branch `feature/paycheck-autopilot-phase-1`.

Ruling on identifiers in ops alerts (raised while writing the T04 appendix): an ops alert may carry FRED's internal ids (user id, inbox row id, schedule id) and the opaque Plaid `item_id`, because the operator needs them to act and none identifies a person on its own. ## Tasks added during execution

`task-24-detection-review-fixes.md` (runs after T12, before T13): three defects the T10 and T12 reviews found in plan-mandated code (an unrecognized Plaid status rejected a stream, a stream with no payer token was seeded onto a shared row, a missed period made a stream dormant although a later deposit had arrived).

Known detection limits recorded for shadow tuning, not fixed in Phase 1: (1) cadence derivation rejects a payer when one off-cycle deposit from the same payer (a bonus or reimbursement) sits among its last six deposits, so that payer reads as undetectable until the extra deposit ages out; (2) the holiday calendar copies the existing schedule one, which has no Juneteenth and no observed-day shifts, so a predicted date can be one business day off near those dates; (3) when Plaid's stream description tokenizes differently from the transactions' descriptors, the first streams read can seed a second row for the same payer.

## Global Constraints

Every task's requirements implicitly include this section.

- **Migration.** The only Phase 1 migration is `V11__ops_alerts_and_admin_actions.sql` (V9 and V10 belong to Goals v3, R15; renumbered from V10 on 2026-11-22 before the merge into develop); T01 starts by listing `backend/src/main/resources/db/migration/` and stops if the number is already taken. V11 is two `CREATE TABLE IF NOT EXISTS` (InnoDB, `utf8mb4_0900_ai_ci`, no ALTER, no foreign key, no view change). Any later ALTER uses the V3 `information_schema` + `PREPARE`/`EXECUTE`/`DEALLOCATE` guard; views are repeatable `R__v_<name>.sql`. `spring.jpa.hibernate.ddl-auto=validate` stays in every profile, and no task changes a Flyway setting.
- **Entity mapping.** NOT NULL booleans use `columnDefinition = "BOOLEAN DEFAULT FALSE"`; nullable tri-state booleans (`plaid_transactions_consented`, `plaidIsActive`, `pending`) use `columnDefinition = "BOOLEAN"`; SMALLINT maps to `short`, TINYINT `anchorDow` is `Short` with `columnDefinition = "TINYINT"`; `trailingCv` is precision 6, scale 4; enums are `@Enumerated(EnumType.STRING)` with a matching `@Column(length)`; Phase 0 style (`@Getter @Setter @NoArgsConstructor`, explicit `@Column`, bare `Long` ids). Every stored Plaid string goes through `ColumnText.fit(String, int)` to its V6 width.
- **Status, not `is_paused`.** `investment_schedules.is_paused` no longer exists. Read `InvestmentSchedule.getStatus()` (`PENDING_BANK`, `ACTIVE`, `PAUSED_BY_USER`); never build on the deprecated `getIsPaused()` or `isPausedForAnyReason()`. The wire key `isPaused` in T16's status response is computed as `getStatus() != Status.ACTIVE`. Phase 1 never writes `status`; its writers stay `pauseSchedule`, `resumeSchedule`, new row creation and `AchRelationshipService.adopt`.
- **Holds are orthogonal.** `hold_reason` is the system's stop and never writes or is written by `status`. `BLOCKING_HOLDS` stays `ACH_RETURN_UNAUTHORIZED`, `ACH_RETURN_ACCOUNT`, `MANUAL_REVIEW` (`BANK_CHANGE` is not blocking). Any "is this hold blocking" question calls `InvestmentSchedule.isBlockingHold(HoldReason)` (T23); nobody restates the three names. Hold writers are an allowlist: the four Phase 0 writers plus `PlaidItemStateService` (T13) and `AdminPaycheckService` (T18), pinned by `PhaseOneMoneyInvarianceTest.onlyAllowlistedFilesCallSetHoldReason`. An Item-state hold is written only when no hold is set, and a repair clears only the hold it wrote. A bank change never downgrades a blocking hold (R20).
- **One runnable rule.** `InvestmentSchedule.isReadyForInvestment(LocalDate todayET)` is the only place that decides whether money moves (`status == ACTIVE`, `achRequestId != null`, no blocking hold, due today). Phase 1 does not change it; T03's `isReadyForInvestmentBodyUnchanged` pins its method text (not line numbers). Call it; never restate it.
- **Mode.** DETECTED is never produced in Phase 1; `mode` stays `MANUAL`, and nothing in Phase 1 calls `setMode(`. The due-today query keeps `status = 'ACTIVE' AND mode = 'MANUAL'`.
- **Schedule writes (R19).** `InvestmentSchedule` carries `@org.hibernate.annotations.DynamicUpdate` (T23). Every Phase 1 schedule writer loads the row inside the transaction that writes it, immediately before writing, and sets only its own fields. The per-user lock is the user row, `userRepository.findByIdForUpdate(id)`, everywhere, `evaluate` included.
- **Events through the outbox.** Any new way to stop or start a schedule emits `schedule_paused` or `schedule_resumed` through `AnalyticsOutboxService.record(...)` inside the transaction that changes the state, with exactly two properties in this order: `initiator` then `reason`, both from `ServerAnalyticsEvent` constants, and only on a real transition (a no-op is silent; each site has a transition test and a no-op test). Non-blocking holds emit nothing (R3). Phase 1 adds exactly one event (`paycheck_stream_switched {frequency, reason}`, T11) and two reasons (`REASON_SUCCESSION = "succession"`, T11; `REASON_REVIEW_CLEARED = "review_cleared"`, T18) and no property key. Each addition lands in `ServerAnalyticsEvent` (and `ALL`), `FREDdocs/analytics-events.md`, `SERVER_EVENT_NAMES` in `frontend/src/app/services/analytics/analytics-events.ts` and the `reason` domain of `LEGITIMATE_VALUES` in `AnalyticsOutboxForbiddenPayloadTest`; `npm run test:events-documented`, `ServerAnalyticsEventParityTest` and `AnalyticsPrivacyGuardParityTest` must pass.
- **Outbound privacy guard.** `AnalyticsPrivacyGuard` strips undeclared or forbidden properties and shaped values (emails, SSN or phone shapes, JWTs, any run of 8 or more digits). Never send a name, email, employer or institution name, payer descriptor, raw amount, Plaid or row id, date or free text in any property; amounts go as `AnalyticsBands.amount(...)` bands and day counts as `AnalyticsBands.daysBetween(...)`. A new property name goes on `ServerAnalyticsEvent.PROPERTY_KEYS` and into `analytics-events.md` in the same change.
- **Logging and alert content (spec 12.3).** Log lines at INFO and above, and every ops alert `message` and `context`, carry ids, codes, states, counts and closed words only: never a descriptor, payer name, amount, cursor, token or a free-text Plaid error body. `message` is cut to 500 characters and `subjectId` to 80.
- **Eastern clock.** `EasternTime.ZONE` (`America/New_York`) wherever money, notifications or day boundaries run; every cron declares `zone = "America/New_York"` and computes one `todayET` per run; gauges bind an ET `nowET` parameter instead of SQL `NOW()`; no bare `LocalDate.now()` or `LocalDateTime.now()` in any file a Phase 1 task touches.
- **Frequency.** `InvestmentSchedule.frequency` stays a `VARCHAR(20)` String holding WEEKLY, BIWEEKLY, SEMI_MONTHLY or MONTHLY; `InvestmentFrequency` is for parsing and math only; factors 4.33 / 2.17 / 2 / 1 stay pinned by `FrequencyFactorParityTest` and `investment-frequency.utils.ts`.
- **Jobs.** Every `@Scheduled` body starts with `schedulerGate.isEnabled()` (`investment.scheduler.enabled`), then `jobLockService.tryAcquire(JobLocks.X, lease)` with `release` in `finally`; one lock name per job. New locks: `OPS_HEARTBEAT = "ops.heartbeat"` (5 min), `PLAID_WEBHOOK_INBOX = "plaid.webhook-inbox"` (5 min), `PAYCHECK_RECONCILE = "paycheck.reconcile"` (60 min). Crons: heartbeat `0 7 9 * * *`, reconcile `0 30 22 * * *`, inbox drainer `fixedDelay = 15000`. `paycheck.autopilot.enabled=false` additionally stops the drainer (rows stay RECEIVED), the pipeline (`REFUSED_DISABLED`, no Plaid call) and the reconcile; the heartbeat still runs.
- **No HTTP inside a database transaction.** No Plaid or Alpaca call inside a transaction: call first, then a `TransactionTemplate` under `userRepository.findByIdForUpdate(id)` with a `plaidItemId` re-check (the `PlaidItemLifecycleService.recordConsentAfterLink` shape). The RECONNECT email is sent after commit; ops alert delivery runs on `opsAlertExecutor` (core 1, max 1, queue 200), never inside the caller's transaction. Phase 0's two documented exceptions stand unchanged (`cancelAllActive` inside the exchange; `UserDeletionService` calling Alpaca before its delete). Tests prove "outside a transaction" with `RecordingTransactionManager` (T06).
- **Pools.** `plaidExecutor` core 4, max 4, queue 100 (T14 raises core from 2); the drainer runs four Items at once, serialized per Item. Hikari stays at 10.
- **R8 exclusions.** Detection, the pipeline and the reconcile skip a user when `DetectionEligibility.exclusion(user, props)` reports `DISABLED`, `ACCOUNT_REJECTED`, `OPTED_OUT`, `NO_TOKEN` or `ITEM_STATUS` (Item not OK or PENDING_DISCONNECT); the check runs at pipeline entry (`REFUSED_EXCLUDED`), so no excluded user starts a billed subscription.
- **Notices.** `NotificationGate.suppressed(user, schedule)` suppresses every DETECTED-only notice under shadow; RECONNECT is the only Phase 1 user notice and is never sent to a REJECTED account or a user with no schedule row (R18).
- **`BrokerEnvironmentGuard`.** Edited by T04 (`checkProdOpsAlertProvider`: prod refuses `logging`, and refuses `webhook` with a blank or http URL) and T17 (`checkProdAdminKey`: prod refuses a blank `ADMIN_TOOLS_KEY` and the CI value `ci-local-admin-tools`), in that order; no other task edits it.
- **Error bodies.** 4xx and 5xx bodies use `ErrorCodeResponse{code, message}`. Phase 0 codes stay (`UPDATE_MODE_UNAVAILABLE`, `LINK_IN_PROGRESS`, `DELETION_DEFERRED`). Phase 1 adds `STALE_ITEM` (409), `PLAID_ERROR` (502), `NO_PLAID_ITEM` and `ITEM_ALREADY_REMOVED` (409), `HOLD_RESERVED` (422), `HOLD_BLOCKING`, `ACCOUNT_REJECTED`, `NO_SCHEDULE`, `NOT_IN_REVIEW` (409). The webhook endpoint still answers only 200, 401 and 503 with empty bodies. `/api/admin/**` answers 404 on a bad or missing `X-Admin-Key` and 400 on a missing `X-Admin-Actor`.
- **Tests.** JUnit 5 + Mockito, `new Service(...)` plus `ReflectionTestUtils.setField`, `retrofit2.Call` mocked with `Response.success` or `Response.error`. No new `@SpringBootTest` except `@RequiresCiDatabase` classes copying the existing rollback-test shape where a real transaction boundary or the database is the thing under test. The whole backend suite runs against a scratch MySQL schema created and dropped in the same shell block (never `investing_dev` or `api-dev`); read the counts from `build/test-results/test/*.xml`, never the console, and never accept a run with skips. Counts in `PhaseOneMoneyInvarianceTest` (6 at T03) and `ScheduleTransitionAnalyticsTest` are stated as "the count before this task plus N".
- **Deletions.** Never add a hard delete without asking Andy. The one Phase 1 code deletion is `DevUserController` and its test (moved to `POST /api/admin/users/{id}/delete`, T17); user deletion stays only `UserDeletionService.delete(user, reason)`, which requests the vendor person deletion inside its transaction. Row deletes in Phase 1 are the spec's own: the relink purge in `resetForNewItem` (spec 2.4 step 3, 7.9) and the 24-month `paycheck_events` retention in the reconcile. Grep both trees for a removed name before committing.
- **House style and commits.** No em dashes anywhere: code, comments, copy, docs, commit messages. One conventional commit per task, no exceptions. The executing session appends its own attribution trailer. Never push without asking Andy.
- **Visibility.** Phase 1 is invisible to MANUAL users except the reconnect card, the RECONNECT notice and the update-mode consent path they lead to; Pause and Resume stay as they are.
- **Shared dirty tree.** Never `git checkout`, `git restore`, `git stash` or `git reset`; hunk-verify `git diff HEAD -- <file>` before staging; stage only the files each task names, by full path; never stage `ITPM/agent-memory/*`, `application-local.properties` or `.github/workflows/verify.yml`. ## Rulings (R1 to R21)

The controller's rulings where the spec and the handoff leave a gap, restated from `inputs.md`. Each carries its cost if wrong; where `inputs.md` names none, the cost given is the planner's reading and is marked (inferred).

- **R1. Shadow writes detection onto the MANUAL row.** Streams, events and cycles are per user, independent of `mode`; when a schedule row exists, `evaluate` mirrors `detection_state`, `primary_stream_id`, `next_expected_date` and `last_cadence_check_at` onto it in every mode, and `mode` stays MANUAL. Spec 3.2's "detection_state null in MANUAL" reads "null until detection has run"; nothing reads these fields on the wire until Phase 2. Cost if wrong: a Phase 2 reader learns to ignore stale shadow values; nothing user-visible.
- **R2. No detection-originated hold on a MANUAL schedule.** DORMANT and AWAITING_AUTHORIZATION are not written in Phase 1 (dormancy lives on the stream, the cycle and the shadow report). The Item-state holds of spec 5.7 (ITEM_LOGIN_REQUIRED, PERMISSION_REVOKED, CONSENT_REQUIRED) are written in both modes; they are not blocking.
